# Архитектурное решение по кешированию

Кеширование дует добавлено при запросах к БД.

## Мотивация
Кеширование списка активных заказов позволит ускорить загрузки страницы со
списком заказов и операторы смогут быстрее брать в работу новые заказы.

## Предлагаемое решение

| Подход         | Плюсы                                                                                                                                                                                                                                                                                                          | Минусы                                                                                                                                                                                                           |
|----------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Cache‑Aside    | 1) Простота реализации - логика кеширования вынесена в клиентский код.<br/>2) Гибкость - приложение само решает, когда читать/писать в кеш. <br/>3) Низкие накладные расходы - кеш обновляется только при реальном запросе. <br/> 4) Устойчивость к сбоям кеша - при падении кеша система продолжает работать. | 1) Риск устаревания‑данных - между чтением из БД и записью в кеш могут быть изменения. <br/> 2) Повышенная нагрузка на БД при промахе кеша. <br/> 3) Дублирование логики кеширования в клиентах.                 |
| Write‑Through  | 1) Актуальность данных - кеш всегда синхронизирован с БД. <br/> 2) Упрощённая логика клиента - приложение не управляет обновлением кеша. <br/>3) Предсказуемость - нет проблем с устаревшими данными. <br/> 4) Атомарность - операция записи либо полностью проходит, либо откатывается.                       | 1) Повышенная задержка записи - каждая операция проходит через кеш. <br/> 2) Зависимость от кеша - сбой кеша блокирует записи в БД. <br/> 3) Избыточное кеширование - данные могут записываться, но не читаться. |
| Refresh‑Ahead  | 1) Минимизация задержек - данные подгружаются в кеш до запроса. <br/> 2) Высокая производительность для часточитаемых данных. <br/> 3) Снижение нагрузки на БД - меньше прямых запросов. <br/>4) Предзагрузка по расписанию - можно учитывать паттерны использования.                                          | 1) Риск избыточной загрузки <br/> 2) Неэффективность для редких данных - трата ресурсов на невостребованные записи. <br/> 3) Кеш должен работать без ошибок - ошибки могут привести к неконсистентности данных.  |

Нам важно держать список заказов всегда актуальным, так как операторы должны видеть новые заказы. Система должна быть 
отказоустойчивой, чтобы не прекращать обработку заказов при проблемах с кешем. Хотелось бы избежать загрузки
невостребованных данных. 

Cache-Aside в таком случае будет лучим выбором, так как он позволит избежать простоев с обработкой заказов при сбое в 
кеше.
TTL - 1 минута и инвалидация при обновлении данных.
